**Проблема та варіанти вирішення**

Коротко: не надходять сповіщення про наближення терміну придатності, прострочення та про низький запас препарату. Нижче — діагностика, швидкі перевірки й варіанти виправлення.

**Докази / де шукати**

- Фоновий сервіс сповіщень: `BackgroundServices/ExpiryNotificationService.cs` — працює раз на добу.
- Сервіс для створення сповіщень: `Services/ServiceNotification.cs` (запис у таблицю `Notifications`).
- Метод вибірки препаратів, що закінчуються: `Services/ServiceMedicine.GetExpiringMedicines`.
- Налаштування: `appsettings.json` → `Monitoring:ExpiryWarningDays`, `Business:LowStockThreshold`.
- Таблиця збереження: `Notifications` у базі даних.

**Можливі причини відсутності сповіщень**

1. `ExpiryNotificationService` ще не виконався (інтервал — 1 день).
2. Немає препаратів із датою `ExpiryDate` у вказаному вікні (логічний фільтр у `GetExpiringMedicines`).
3. LowStock автоматичного генератора сповіщень немає в коді (поточна реалізація лише дозволяє читати низькі запаси).
4. Сповіщення створюються, але фронтенд їх фільтрує або користувач немає прав на бачення (організаційна/ролева фільтрація).

**Швидкі перевірки (без змін коду)**

- Перевірити логи сервера: шукайте `ExpiryNotificationService started` і `Expiry notification sent for Medicine`.
- Виклик API для перевірки списку, що закінчується, напр.:

```bash
curl "http://localhost:5001/api/medicines/expiring?daysThreshold=7"
```

- Перевірити базу даних прямо:

```sql
SELECT TOP 50 * FROM Notifications ORDER BY CreatedAt DESC;
```

- Створити тестове сповіщення вручну через API (перевірка фронтенду):

```bash
curl -X POST http://localhost:5001/api/notifications -H "Content-Type: application/json" -d '{"type":1,"title":"Тест","message":"Тестове сповіщення","targetRole":"All","relatedEntityType":"Medicine","relatedEntityId":1}'
```

**Тимчасові (швидкі) рішення**

- Тимчасово зменшити інтервал у `ExpiryNotificationService` (для тестування змінити `Task.Delay(TimeSpan.FromDays(1))` на менший інтервал) і перезапустити сервіс.
- Створювати тестові сповіщення через API, щоб перевірити фронтенд і права доступу.

**Середньострокові (код) рішення**

1. Додати admin-endpoint для ручного тригеру перевірки expiring/expired (наприклад `POST /api/admin/notifications/trigger-expiry`) — дозволяє протестувати без зміни інтервалів.
2. Додати окрему фонова задачу `LowStockNotificationService` або розширити `ExpiryNotificationService` для періодичної перевірки низького запасу:
   - Виклик `ServiceMedicine.GetLowStockMedicines(threshold)`;
   - Створення `NotificationType.LowStock` з дедуплікацією (не більше 1 сповіщення на препарат на добу або поки не поповнено).
3. Забезпечити дедуплікацію та idempotency: перевіряти в `Notifications` на наявність `RelatedEntityId/Type` за поточну дату перед створенням.

**Довгострокові покращення**

- Централізований шедулер / job-queue (Hangfire, Quartz) для контролю періодичних задач й історії виконань.
- Телеметрія/моніторинг (AppInsights або прості логи) для відстеження виконань background tasks і невдалих спроб створення сповіщень.
- UI: підказка адміністратору про налаштування порогів і ручний тригер у адмін-панелі.

**Ризики та побічні ефекти**

- Занадто часті перевірки можуть створити навантаження на БД; робіть індексацію на `ExpiryDate`/`OrganizationId` (вже є індекси), або перевіряйте порційно.
- Створення дублікатів сповіщень без дедуплікації — дратівливе UX; обов'язково зберегти перевірки на дату/стан.
- Потрібно врахувати фільтрацію за `OrganizationId` і ролями — фонова служба повинна правильно встановлювати `OrganizationId` або створювати глобальні сповіщення.

**Рекомендований план (поетапно)**

1. Виконати швидкі перевірки: логи, `GET /api/medicines/expiring`, перевірка `Notifications` у БД. (15–30 хв)
2. Додати тимчасовий admin-endpoint `trigger-expiry` та викликати його, перевірити, чи з’являться записи. (30–60 хв)
3. Якщо потрібно — додати `LowStockNotificationService` з дедуплікацією та тестами; додати unit/integration тест для job. (1–2 дні)
4. Впровадити моніторинг виконань і UI-ручки для адміністраторів. (опціонально)
