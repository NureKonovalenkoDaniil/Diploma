# План тестування (Фаза 6: Автоматизовані тести)

Для того, щоб дипломна робота виглядала солідно та технічно довершено, необхідно покрити ключові компоненти системи автоматизованими тестами. Це продемонструє розуміння забезпечення якості ПЗ (QA) на всіх рівнях: Backend, Frontend, Mobile та IoT.

## 1. Стратегія тестування та Стек технологій

Ми застосуємо підхід **Full-Stack тестування**, покривши найважливіші частини кожного компонента:

### 1.1 Backend (ASP.NET Core)
- **xUnit** — основний фреймворк для запуску тестів.
- **Moq** — для створення моків залежностей.
- **FluentAssertions** — для зручних перевірок (asserts).
- **WebApplicationFactory** + **EF Core In-Memory** — для інтеграційних тестів API.

### 1.2 Frontend (React + TypeScript)
- **Vitest** — надшвидкий тестовий фреймворк для Vite.
- **React Testing Library** — для тестування компонентів так, як з ними взаємодіє користувач.
- **MSW (Mock Service Worker)** — (опціонально) для мокування API-запитів.

### 1.3 Mobile (Android Kotlin)
- **JUnit 4 / 5** — для Unit-тестів.
- **MockK** — сучасна бібліотека мокування для Kotlin.
- **kotlinx-coroutines-test** — для тестування асинхронного коду у ViewModel.

### 1.4 IoT Emulator (C++ / PlatformIO)
- **Unity** — легкобогий фреймворк для Unit-тестування C++ коду на мікроконтролерах (доступний вбудовано у PlatformIO).

## 2. Структура тестових проєктів

Ми створимо єдиний або два окремих проєкти в папці `Tests`:
1. `MedicationManagement.UnitTests` — для ізольованого тестування бізнес-логіки (Сервіси).
2. `MedicationManagement.IntegrationTests` — для тестування ендпоінтів (Контролери + База даних + Ролі).

## 3. Що саме будемо тестувати? (Scope)

### 3.1. Unit-тести (Бізнес-логіка та Сервіси)
Unit-тести перевірятимуть роботу сервісів в ізоляції (без реальної БД, з використанням EF Core In-Memory або Moq).

**Пріоритетні сервіси для покриття:**
- **`ServiceMedicine`**:
  - Атомарні операції: `MoveAsync` (перевірка, що змінюється `StorageLocationId` і створюється подія `Moved`).
  - Зміна залишку: `ChangeQuantityAsync` (перевірка валідації на від'ємний залишок, коректне створення подій `Received`, `Issued`, `Disposed`).
  - Перевірка Multi-tenancy: чи підставляється правильний `OrganizationId` під час `Create`.
- **`ServiceIoTDevice`**:
  - Логіка Claim: перевірка `ClaimDeviceSecret` (успішний claim, спроба claim для вже прив'язаного пристрою, спроба для неактивного).
  - Створення пристрою з генерацією хешу.
- **`BackgroundServices` (`StorageConditionMonitoringService`)**:
  - Оскільки це фонова задача, ми можемо протестувати її внутрішню логіку: 
    - Якщо показники за межами `Min/Max`, має створитись `StorageIncident`.
    - Якщо показники повернулися в норму, `StorageIncident` має отримати статус `Resolved`.
- **`ServiceNotification`**:
  - Створення сповіщень та автоматичне призначення `OrganizationId`.

### 3.2. Integration-тести (API, Авторизація, Multi-tenancy)
Інтеграційні тести перевірятимуть весь ланцюжок: `HTTP Запит -> Контролер -> Сервіс -> In-Memory БД -> HTTP Відповідь`.

**Пріоритетні сценарії для диплома:**
- **Авторизація та Ролі (`AuthController`)**:
  - Реєстрація нового користувача (перевірка створення `ApplicationUser` з новим `OrganizationId`).
  - Логін непідтвердженого користувача (має повертати `Unauthorized/BadRequest`).
  - Відправка запиту на захищений ендпоінт без токена (має повертати `401 Unauthorized`).
- **Multi-tenancy Ізоляція (Критично для диплома!)**:
  - Сценарій: Створюємо двох користувачів з різними `OrganizationId`. Користувач А створює локацію. Користувач Б робить `GET /api/storagelocation`.
  - Очікування: Користувач Б отримує порожній список. Це доведе комісії, що наша архітектура ізоляції даних працює безпечно.
- **Role-Based Access Control (RBAC)**:
  - Сценарій: Користувач (роль `User`) намагається створити новий `IoTDevice` через `POST /api/iotdevice`.
  - Очікування: Повертається `403 Forbidden`.

### 3.3. Frontend-тести (SPA React)
Тестування UI-логіки без залежності від реального бекенду.
- **Тестування `AuthContext`**: перевірка логіки збереження токену, парсингу ролей (чи вірно визначається `isManager`/`isAdmin` на основі JWT).
- **Тестування Компонентів (наприклад, `MedicinesPage`)**:
  - Перевірка відображення кнопок "Видалити"/"Редагувати" залежно від ролі (Admin бачить, звичайний User — ні).
  - Рендеринг порожнього стану (Empty State), коли немає даних.

### 3.4. Mobile-тести (Android)
Оскільки мобільний додаток нещодавно переведено на архітектуру з `ViewModel` та `Coroutines`, ми можемо протестувати бізнес-логіку UI ізольовано від Android Framework:
- **Тестування `MedicinesViewModel`**:
  - Перевірка логіки "Quick Action" (чи правильно формується запит `PATCH` та чи викликається створення події).
  - Обробка помилок мережі (чи коректно оновлюється `LiveData` з повідомленням про помилку, коли API повертає `500` або падає Exception).
- **Тестування `NotificationsViewModel`**:
  - Перевірка сортування (чи дійсно непрочитані сповіщення піднімаються вгору списку).

### 3.5. IoT Emulator-тести (C++)
Базове тестування функцій обробки даних у мікроконтролері.
- Перевірка форматування JSON перед відправкою.
- Перевірка внутрішньої логіки (наприклад, чи правильно зчитуються "фейкові" показники DHT22, якщо ми винесемо їх у окрему функцію).

## 4. План дій (Roadmap)

1. **Крок 1: Backend Setup.** Створення тестових проєктів `.csproj`, додавання NuGet пакетів (`xunit`, `Moq`, тощо) та написання Backend Unit/Integration тестів.
2. **Крок 2: Frontend Setup.** Ініціалізація `Vitest` у проєкті Vite, написання базових тестів для `AuthContext` та кількох компонентів.
3. **Крок 3: Mobile Setup.** Додавання залежностей `junit`, `mockk`, `coroutines-test` у `build.gradle` та тестування `ViewModel`.
4. **Крок 4: IoT Setup.** Налаштування `test_framework = unity` у `platformio.ini` та написання базового C++ тесту.

> [!IMPORTANT]
> **Питання до вас:** 
> Такий Full-Stack підхід ідеально підійде для диплома, оскільки покаже ваше вміння писати тести для геть різних екосистем (C#, TypeScript, Kotlin, C++). Починаємо реалізацію з бекенду (Крок 1)?
